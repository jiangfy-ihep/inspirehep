# Local development in an AlmaLinux 10 Kubernetes container

[中文](local-setup-almalinux10-cn.md) · [Daily startup](running-the-dev-server.md)

This workspace is a **Kubernetes-managed container**, with AlmaLinux **10.2**
userland on x86_64. It does not run systemd: PID 1 is `bash`, and
`systemd-detect-virt` reports `docker` (checked outside the agent sandbox on
2026-11-13). The kernel belongs to the outer host; `/etc/os-release` describes
the workspace userland. Recheck these facts after redeployment rather than
treating the workspace as a full virtual machine.

Docker runs as a nested daemon in this container. A running daemon and a
successful container workload are separate validation steps; neither installing
Docker packages nor identifying the OS certifies a complete installation.

The application versions below come from this checkout, not the OS defaults.

| Component | Current repository configuration |
| --- | --- |
| Backend and backoffice Python | 3.11; see both `pyproject.toml` files |
| Python dependency manager | Poetry; both lockfiles were generated by 2.4.1 |
| UI | Node 24.15.0, Yarn Classic, React 19, Vite, Vitest |
| Search | OpenSearch 3.9.0 with the plugins in `docker/opensearch.Dockerfile` |
| Databases | Backend PostgreSQL 14.13; backoffice PostgreSQL 15.15 |
| Other infrastructure | Redis 8, RabbitMQ 4.2, S3-compatible storage |
| Workflows | Airflow 3.4.0 base image; run in the repository's containers |

The recommended upstream workflow runs applications in Docker. This guide also
covers backend, UI, and backoffice processes running directly in the workspace,
with infrastructure in nested Docker. Here, "native" means a workspace process,
not a process on the Kubernetes node. This does not start Airflow or the complete
curation workflow.

## 1. Inspect the host and choose a workflow

Run from the repository root unless a step explicitly changes directory:

```bash
cat /etc/os-release
uname -m
cat /proc/1/comm
systemd-detect-virt
findmnt -n -o FSTYPE,OPTIONS /sys/fs/cgroup
git status --short --branch
command -v docker poetry node yarn tmux
sysctl vm.max_map_count
```

Reuse existing project environments and Docker installations. The full stack
needs about 18 GB RAM; the outer Pod's resource limits must accommodate it.
Do not replace the system Python. Inspect PID 1 by process name rather than
dumping its command line, which can contain bootstrap credentials.

For a full container setup, use the root README and `Makefile`. This fork has a
local `docker-compose.override.yml` that changes S3 credentials and storage.
The upstream topology should omit that override. First configure the Airflow
variables referenced by `docker-compose.yml`,
including `FERNET_KEY`, in the ignored root `.env` or your shell. This native
setup guide does not provision the complete Airflow environment. Then run:

```bash
COMPOSE_FILE=docker-compose.yml make run
```

First complete the Docker checks in section 2. That command starts and
initializes services; run it only for the intended
development instance. The native workflow below explicitly uses the local
override and its `inspirehep` S3 credentials. Do not mix these two configurations
against the same running containers.

## 2. Administrator tasks: user runs these commands

Package installation, Docker startup/access, and firewall inspection may need
`sudo`. Ask the user/administrator to run those commands and report results.
Changes to Pod capabilities, cgroup delegation, node kernel settings, and cluster
networking require the cluster administrator; `sudo` inside this workspace does
not grant control of the Kubernetes node. Everything after this section runs
as the normal development user.

### Native build and runtime prerequisites

```bash
sudo dnf install -y dnf-plugins-core
sudo dnf config-manager --set-enabled crb
sudo dnf install -y \
  gcc gcc-c++ make pkgconf-pkg-config libpq-devel \
  file-libs gettext poppler-utils git curl jq tmux
```

`libpq-devel` supplies PostgreSQL client headers and `pg_config` for backoffice's
`psycopg[c]`. `file-libs` supplies the runtime library used by `python-magic`;
`file-devel` is not needed merely to load libmagic. Python 3.11 will be installed
separately below. If a package is unavailable on a configured mirror, inspect
`dnf provides '*/pg_config'` and the enabled repositories before changing names.

NumPy normally installs from a compatible wheel. Install `openblas-devel` only
if a source build specifically requires it. Likewise, request any additional
native headers named by a build error; do not work around it by changing locked
Python dependency versions.

### Install Docker packages only if absent

Use the [Docker RHEL installation instructions](https://docs.docker.com/engine/install/rhel/)
as the package reference. Inspect existing installations first:

```bash
sudo dnf config-manager --add-repo https://download.docker.com/linux/rhel/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

The workspace currently has Docker Engine/CLI 29.9.3 and Compose 5.7.1.
Reinstallation does not fix daemon or socket-access errors. There is no systemd
service manager here: `systemctl enable --now docker` cannot start the daemon,
and creating an enablement symlink does not arrange startup after Pod restart.

### Check daemon state and socket access before starting anything

```bash
docker context show
ls -l /var/run/docker.sock
id -nG
getent group docker
docker info
```

On 2026-11-13, `dockerd` and `containerd` were running and the socket existed
with mode `660`, owned by `root:docker`. The checked session was denied access:
the account was listed in the Docker group database, but its existing process
had not acquired the supplementary group. This differs from the earlier
missing-socket error. Do not start a second daemon to fix a permission error.

If group membership has not been granted, the user/administrator can run this
as the developer's login account:

```bash
sudo usermod -aG docker "$(id -un)"
```

If the account is already listed, refresh the current terminal instead of
adding it again:

```bash
newgrp docker
id -nG
docker info
```

`newgrp` starts a subshell. A new SSH login also loads updated groups; existing
shells, tmux servers, and other long-lived processes retain their old groups.
Docker group access grants control equivalent to root; use the site's approved
alternative if unsuitable. Do not make the socket world-writable.

### Start the nested daemon manually when it is not running

After confirming no daemon is running, have the user/administrator start it in
a dedicated terminal, following
[Docker's manual startup instructions](https://docs.docker.com/engine/daemon/start/):

```bash
sudo dockerd
```

This runs in the foreground and prints logs to that terminal. Keep it open.
To survive an SSH disconnect, first create a dedicated tmux session with
`tmux new-session -s inspirehep-docker`, then run the same command there and
detach with `Ctrl+B`, then `d`. Reattach with
`tmux attach-session -t inspirehep-docker`. Run one daemon using the site's
approved configuration; do not start a new one on each application restart.

In another terminal with socket access, verify the server and test a container:

```bash
docker version
docker compose version
docker info
docker info --format '{{.DockerRootDir}}'
docker run --rm hello-world
```

The last command downloads and runs an image; it was not executed during the
documentation checks. Success verifies a basic workload, not the full Compose
stack. `Ctrl+C` in the daemon terminal stops Docker. For automatic recovery
after Pod replacement, the cluster administrator must configure an approved
startup/supervision mechanism; tmux survives a disconnect, not Pod replacement.

### Nested Docker prerequisites and failures

The current `/sys/fs/cgroup` mount is cgroup v2 and read-only. PID 1 has
`CAP_SYS_ADMIN` and `CAP_NET_ADMIN` in its capability set, but that alone does
not prove all inner-container operations work. A daemon can start while
workloads fail when creating cgroups, mounts, or bridge networking.

If startup or the smoke test fails, report the first error to the cluster
administrator. They must check the approved nested-container capability and
security profile, cgroup access/delegation, storage driver/filesystem, and
networking. Do not remount node cgroups, enable blanket privileged mode, or
disable Docker firewall management as generic fixes. Workspace user-group
permissions cannot fix those cluster-level constraints.

Do not assume Docker stores data in `/data/docker`, point its data root at the
shared project directory, or change storage drivers against existing Docker
data. The administrator should provide suitable storage and a persistence plan;
the workspace writable layer may be replaced with the Pod. If nested Docker is
unsupported, use an administrator-provided engine or Kubernetes infrastructure.
A remote engine needs a matching topology: `localhost` ports and Compose bind
mounts refer to the engine's machine, not automatically to this workspace. The
commands below assume a working nested engine in this workspace.

### OpenSearch kernel setting, only if too low

OpenSearch requires `vm.max_map_count` of at least `262144`. The current shared
kernel already reports that value, so no change is needed:

```bash
sysctl vm.max_map_count
```

If too low after rescheduling, ask the cluster administrator to configure the
relevant node's kernel setting and persistence. Writing a sysctl file inside
this container does not configure node boot or create a systemd service.

### Check firewall-cmd and the actual network layers

The following read-only checks were performed on 2026-11-13:

```bash
command -v firewall-cmd
firewall-cmd --state
ls -l /run/dbus/system_bus_socket
ss -ltn
```

`firewall-cmd` and firewalld 2.4.3 are installed, but firewalld is not running
and the system D-Bus socket does not exist. The state query returns:

```text
Error: DBUS_ERROR: Failed to connect to socket /run/dbus/system_bus_socket: No such file or directory
```

`firewall-cmd` communicates with firewalld over D-Bus. Installing its CLI does
not supply a running service. `--add-port` and `--reload` are not the applicable
port-opening procedure here. Do not start D-Bus/firewalld merely to run those
commands, or use `firewall-offline-cmd` expecting a live change; offline
configuration alone does not apply runtime rules.

Distinguish these network layers:

1. The app must listen on the intended address/port in the workspace network
   namespace; inspect `ss -ltn` and test with `curl` inside the workspace.
2. Workspace iptables/nftables input rules may come from its bootstrap
   configuration. Absence of firewalld does not mean those rules are absent.
   Nested Docker also creates forwarding/NAT rules for inner containers.
3. Kubernetes CNI routing, NetworkPolicy, and the cluster's Service/Ingress or
   other workspace access mechanism determine reachability from outside the
   Pod. An inner `docker -p` publishes in the workspace namespace; it does not
   automatically create an external Kubernetes endpoint.

For a blocked port, ask the user/administrator for these read-only rule listings,
then request a targeted change in the correct layer:

```bash
sudo iptables -S
sudo iptables -t nat -S
sudo nft list ruleset
```

These privileged rule listings were not run during the documentation checks.
Native UI/API/backoffice may need ports 3000/8000/8001 respectively; Docker's
infrastructure publishing needs separate review. Preserve SSH and Docker rules;
do not flush tables or insert blanket accept rules. Persistent changes belong
in administrator-managed workspace/cluster configuration. See
[Docker networking](https://docs.docker.com/engine/network/packet-filtering-firewalls/)
and [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

## 3. User tools and project environments

Use Poetry for both Python projects. uv may install the Python interpreter and
standalone tools; do not use `uv sync`, `uv add`, or `pip install` to manage this
repository's Python dependencies.

If uv is absent, follow its [installation instructions](https://docs.astral.sh/uv/getting-started/installation/).
With uv available:

```bash
uv python install 3.11
uv python find 3.11
uv tool install --python 3.11 'poetry==2.4.1'
export PATH="$HOME/.local/bin:$PATH"
poetry --version
```

Poetry 2.4.1 matches the lockfile generator. The Dockerfiles pin their own
Poetry versions. Do not regenerate either lockfile just to silence a local tool
version warning. If Poetry is already installed, inspect its version and the
existing project environments before replacing anything.

From the repository root, install each project's locked dependencies:

```bash
(cd backend && poetry env use "$(uv python find 3.11)" && poetry install --with dev)
(cd backoffice && poetry env use "$(uv python find 3.11)" && poetry install --with dev)
(cd backend && poetry run python --version && poetry env info --path)
(cd backoffice && poetry run python --version && poetry env info --path)
```

Deactivate any unrelated virtualenv before selecting the project environments.
Installing from the existing lockfiles does not require `poetry update`.

Install/load [nvm](https://github.com/nvm-sh/nvm#installing-and-updating) in your
user shell, then use the Node version in the UI Dockerfiles:

```bash
nvm install 24.15.0
nvm use 24.15.0
npm install --global yarn@1.22.22
(cd ui && yarn install --frozen-lockfile)
```

With nvm, Node and Yarn are user installations; no `sudo npm` is needed. Vite
does not require the old `--openssl-legacy-provider` setting. The legacy Angular
application in `record-editor/` has separate tooling; the newer React editor
lives in `ui/src/editor/`.

For Python formatting checks, install pre-commit as a standalone user tool:

pre-commit install

## 4. Start the native workflow's infrastructure

Use the main Compose file, which publishes RabbitMQ ports and defines the
separate backoffice database and broker. Define this function in each shell
where infrastructure commands are needed, while at the repository root:

```bash
dc() { docker compose -f docker-compose.yml -f docker-compose.override.yml "$@"; }
dc config --quiet
dc up -d db db-backoffice cache mq backoffice-mq es s3
dc ps
```

This starts infrastructure only. It uses the checked-in override's MinIO
credentials (`inspirehep` / `inspirehep`). Wait for the database, cache, search,
and S3 health checks; inspect `dc logs es s3 mq` on failure.

Compose may warn about an unset `FERNET_KEY` while reading the main file even
though this command does not start Airflow. Configure it before starting any
workflow services.

| Workspace endpoint | Service |
| --- | --- |
| `localhost:5432` | Backend PostgreSQL (`inspirehep` database) |
| `localhost:5434` | Backoffice PostgreSQL (`backoffice` database) |
| `localhost:6379` | Redis |
| `localhost:5672`, `localhost:15672` | Backend RabbitMQ, management UI |
| `localhost:5673`, `localhost:15673` | Backoffice RabbitMQ, management UI |
| `localhost:9200` | OpenSearch |
| `localhost:9000`, `localhost:9001` | S3 API, MinIO console |

These development Compose files publish infrastructure ports on all workspace
interfaces; the table is not a guarantee of loopback-only binding. Ask the
administrator to restrict exposure on a shared host. Service names such as
`db`, `es`, and `hep-web` are Docker DNS names; native applications use the host
endpoints above.

The older `scripts/dev.sh` starts a reduced topology from
`docker-compose.services.yml` plus the override. That combination does not
publish RabbitMQ or provide the separate backoffice database/broker. Do not
use it to initialize or reconfigure this topology; use the manual startup
commands below.

## 5. Configure native application environments

Create local `backend/.env` and `backoffice/.env` files. Both are ignored by Git.
These files must use shell-compatible assignments because the examples load
them with `source`. Never put private values into tracked configuration files.

Example `backend/.env`:

```bash
INVENIO_SQLALCHEMY_DATABASE_URI='postgresql+psycopg2://postgres:postgres@localhost:5432/inspirehep'
INVENIO_SEARCH_ELASTIC_HOSTS="['localhost:9200']"
INVENIO_BROKER_URL='amqp://guest:guest@localhost:5672/'
INVENIO_CELERY_BROKER_URL='amqp://guest:guest@localhost:5672/'
INVENIO_CELERY_RESULT_BACKEND='redis://localhost:6379/2'
INVENIO_CACHE_REDIS_URL='redis://localhost:6379/0'
INVENIO_ACCOUNTS_SESSION_REDIS_URL='redis://localhost:6379/1'
INVENIO_S3_HOSTNAME='http://localhost:9000'
INVENIO_S3_ACCESS_KEY='inspirehep'
INVENIO_S3_SECRET_KEY='inspirehep'
AWS_DEFAULT_REGION='us-east-1'
INVENIO_FEATURE_FLAG_ENABLE_FILES=True
INVENIO_FEATURE_FLAG_ENABLE_FULLTEXT=True
INVENIO_FEATURE_FLAG_ENABLE_LOCAL_LOGIN=True
INVENIO_SERVER_NAME='localhost:8000'
INVENIO_JSONSCHEMAS_HOST='localhost:8000'
INVENIO_SECRET_KEY='replace-with-a-generated-local-secret'
INVENIO_AUTHENTICATION_TOKEN='replace-with-a-generated-local-token'
```

Generate separate values for the last two settings with
`poetry run python -c 'import secrets; print(secrets.token_hex(32))'` in
`backend/`, and put them only into the ignored file. Set the token **before**
initialization: fixtures store it as the local admin's API token.

For LAN clients, change `INVENIO_SERVER_NAME` and `INVENIO_JSONSCHEMAS_HOST` to
the hostname/IP that those clients can reach, including port 8000. Keep the
S3 and database connection addresses appropriate for where the processes run.

Example `backoffice/.env`:

```bash
DJANGO_SETTINGS_MODULE='config.settings.local'
DJANGO_READ_DOT_ENV_FILE=False
USE_DOCKER=no
POSTGRES_URI='postgresql://postgres:postgres@localhost:5434/backoffice'
REDIS_URL='redis://localhost:6379/4'
CELERY_BROKER_URL='amqp://guest:guest@localhost:5673/'
OPENSEARCH_HOST='localhost:9200'
OPENSEARCH_INDEX_PREFIX='backoffice-backend-local'
INSPIREHEP_BASE_URL='http://localhost:8000'
AIRFLOW_BASE_URL='http://localhost:8070'
FRONTEND_LOGIN_SUCCESS='http://localhost:3000/backoffice'
```

Backoffice otherwise reads the tracked `.envs/local/.django` and `.postgres`
files, whose values target Docker DNS names. `DJANGO_READ_DOT_ENV_FILE=False`
prevents loading those container defaults when this native environment is used.
Airflow is not running in the infrastructure-only setup; its URL becomes useful
only after the workflow services are configured and started.

Poetry does not automatically load these `.env` files. In every native app
shell, run `set -a; source ./.env; set +a` from that app's directory before its
commands. Alternatively, an existing direnv setup can load them; do not assume
direnv is installed or configured.

## 6. Initialize a fresh development instance

The main Compose topology sets `POSTGRES_DB` for both databases on first use of
fresh database storage. Inspect before creating anything:

```bash
dc exec -T db psql -U postgres -tAc "SELECT datname FROM pg_database WHERE datname='inspirehep'"
dc exec -T db-backoffice psql -U postgres -tAc "SELECT datname FROM pg_database WHERE datname='backoffice'"
```

If an existing container's storage predates those settings and a database is
missing, create only the missing one:

```bash
dc exec -T db psql -U postgres -c 'CREATE DATABASE inspirehep;'
dc exec -T db-backoffice psql -U postgres -c 'CREATE DATABASE backoffice;'
```

Backend setup is a **reset operation**. `backend/inspirehep/fixtures.py` flushes
Redis, destroys/recreates database tables and search indices, purges its queue,
and creates file buckets and fixture users. Run it only for a fresh disposable
development instance, with other applications using that Redis stopped. It is
not a daily startup command or a data migration procedure.

In a backend shell:

```bash
cd backend
set -a
source ./.env
set +a
poetry run ./scripts/setup
poetry run inspirehep importer demo-records
```

In a separate backoffice shell, load its environment and initialize it:

```bash
cd backoffice
set -a
source ./.env
set +a
poetry run python manage.py migrate
poetry run python manage.py create_groups
poetry run python manage.py loaddata backoffice/users/fixtures/users.json
poetry run python manage.py opensearch index rebuild --force
poetry run python manage.py opensearch document index --force
```

The index rebuild also replaces existing backoffice indices; use it only during
initial setup or an intentional rebuild. Creating a few native web services does
not configure Airflow tokens, all workflow fixtures, or asynchronous backoffice
workers. Use the full Docker workflow for those end-to-end scenarios.

## 8. Imports, tests, shutdown, and synchronization

Run imports in an environment-loaded backend shell. The CLI writes directly to
the database and index; importing local files does not require a running HTTP
server or an API token:

```bash
poetry run inspirehep importer records -f data/records/literature/374836.json
poetry run inspirehep importer records -d data/records/literature
```

URL imports fetch raw JSON from the **source** API. `--token` authenticates to
that source, not the local backend. A token generated by your local instance
does not grant access to inspirehep.net:

```bash
poetry run inspirehep importer records \
  -u https://inspirehep.net/api/literature/20 --token "$SOURCE_API_TOKEN"
```

`-u` and `-f` can repeat; `-d` accepts one directory per invocation. The optional
`import_records.sh` and `IMPORT.md` symlinks require a separate
`../curation_stats/` checkout; check their targets before using them.

Run the relevant checks from the indicated directory:

| Directory | Check |
| --- | --- |
| `backend/` | `poetry run ./run-tests.sh --all` |
| `backoffice/` with its environment loaded | `poetry run pytest .` |
| `ui/` | `yarn test:unit`; `yarn test` for lint, types, coverage, bundle size |
| Repository root, full workflow containers running | `docker compose -f docker-compose.yml exec -T airflow-worker pytest tests` |
| Repository root | `pre-commit run --files <changed-files>` |

Backend integration tests need their configured services and test databases;
read `backend/tests/conftest.py` and suite fixtures before running them. The
runner normally selects affected integration tests using testmon; `--all`
disables selection. `yarn test:unit` runs Vitest once, not Jest watch mode.
`make run-e2e-test` recreates and initializes containers, so it is not a harmless
check against an existing instance. Cypress defaults to port 8080; a native UI
uses 3000 and requires explicit test URLs and the necessary backoffice/workflow
services.

For daily shutdown, stop the native processes with `Ctrl+C`, then use `dc stop`
to retain the infrastructure containers. `dc down` removes containers;
anonymous database volumes may not be reattached on the next `up`. Back up data
before removing containers or volumes. MinIO alone has an explicitly named
volume in the local override; do not assume all services share that persistence
configuration.

Keep `master` tracking `upstream/master` and `dev` tracking `origin/dev`:

```bash
git fetch upstream
git switch master
git merge --ff-only upstream/master
git switch dev
git pull --ff-only origin dev
git merge upstream/master
# Resolve conflicts and run the affected checks before publishing.
git push origin dev
```

Start with a clean working tree. Merge published history without force-pushing.
For application conflicts, preserve upstream's current implementation. Merge
`.gitignore` rules from both branches and remove duplicate rules.
